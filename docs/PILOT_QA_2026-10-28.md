# Konfydence self-service pilot — QA record

Date: 28 October 2026. Scope: free organisation pilot and custom-scenario workflow. Application QA: PASS in the tested local environments. Customer production deployment acceptance: pending.

## Implemented scope
- Free 28-day pilot, up to 20 participants plus named administrators, up to 12 distinct programme scenarios. Existing library and self-authored scenarios can be mixed. No automatic paid conversion; onboarding and per-seat rollout require a separate agreement.
- Verified-email administrator login and membership checks, tenant isolation, last-administrator protection, self-service draft/preview/publish, immutable published content, invitations and revocation, participant-only pages, expiry enforcement and summary-first evidence dashboards.
- Customer-managed runtime mode with customer-owned PostgreSQL and HTTPS transactional mail gateway. No automatic summary transmission. Explicit aggregate download suppresses fewer than five respondents, bands counts, rounds percentages and excludes identity, raw answers, scenario content and small H.A.C.K. slices.

## Verification results
- 58 automated tests across 12 suites passed.
- ESLint and strict TypeScript checks passed.
- Both hosted and customer-managed Next.js 16.4.3 production builds passed, including all 321 generated pages.
- Both production configurations passed scripts/test-custom-scenarios.cjs against a disposable loopback PostgreSQL-compatible PGlite database. The matrix covers named-admin and tenant isolation, cross-origin rejection, authoring/publishing, limits, free fee enforcement, invitation success, participant-only access, server-side scoring, duplicate response protection, revocation, expiry, reports, evidence and EN/DE pricing.
- Customer-managed production checks verified no Google Analytics bootstrap, same-origin browser connection policy, disabled public lead collection and coarse summary suppression. Invitation delivery used an organisation-gateway fixture over HTTPS with certificate validation enabled.
- Browser QA exercised real email-code login, workspace selection, evidence acknowledgement, pilot activation, custom scenario publication, mixed-library campaign assignment, invitation, participant completion and updated administrator reporting. A separate browser origin confirmed participant links do not grant administrator access.
- Original-schema migrations were applied twice successfully; existing public content was preserved.
- All 240 canonical scored scenarios passed their quality audit; public product claims audit passed.
- Production dependency audit: zero reported vulnerabilities. Full development dependency audit retains six low-severity findings in test tooling; no high or critical findings.

## Defects found and corrected
Participant answer redirects now use relative locations; local host normalisation previously conflicted with the browser policy. Unmeasured dimensions now say Not measured. Participant status reflects all assigned campaigns. CSV exports neutralise spreadsheet formula prefixes. Pilot activation records a zero-fee active pilot with matching dates. Framework dependencies were updated to clear reported production advisories.

## Release boundary
No production deployment or merge was performed. This is application QA evidence, not a guarantee of zero defects or regulatory certification. The browser and database fixtures contained only fictional identities; no real prospect messages were sent.

Before a customer deployment: validate its supported PostgreSQL service and migration/restore procedure, configure its hostname, TLS, secrets and mail gateway, verify inbox delivery, firewall egress, logs, backups and deletion policy, and complete customer acceptance. Set NEXT_PUBLIC_CUSTOMER_HOSTED=1 at both build and runtime and NEXT_TELEMETRY_DISABLED=1. Entra ID, Google Workspace directory sync and LMS connectors are not implemented. Paid rollout billing/entitlement automation is outside this pilot implementation. Separate customer privacy/legal review is required; the dashboard provides evidence records, not compliance certification.

## Reproduction
Use npm ci, npm test -- --runInBand, npm run lint, npx tsc --noEmit, npm run audit:scenarios, npm run audit:claims and npm run audit:production. Build once per deployment mode, then run scripts/test-custom-scenarios.cjs with disposable loopback TEST_DATABASE_URL, TEST_BASE_URL and TEST_AUTH_SECRET. Set TEST_MAIL_GATEWAY=1 for a configured isolated mail fixture and TEST_CUSTOMER_HOSTED=1 for the private build. Never run the integration fixture against a live customer database. Windows sandbox QA used precreated build output directories and a temporary cleanDistDir setting; that test-only setting is not committed.
